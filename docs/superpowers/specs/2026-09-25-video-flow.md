# 영상 흐름 분석 → 우리 게임 대조 (2026-09-25)

**본 영상** — [온천골 스토리 #1](https://youtu.be/eOk1tUs5In4) (머독, 2017-10-23, 30분 04초).
카이로소프트 **Hot Springs Story(온천골 스토리)** 안드로이드 **세로 화면**. 우리와 같은 장르(경영 시뮬)·같은 플랫폼(모바일 세로)·같은 회사 스타일이라 1:1 대조가 된다.

**분석 방법** — `watch` 스킬 파이프라인 그대로.
`yt-dlp`로 원본(311MB) + 자동 자막 내려받고, `ffmpeg`로 두 벌 뽑았다.
- **전체 패스**: 0:00~30:00, 20초마다 1장, 가로 1024px → **90장**
- **집중 패스**: 0:00~5:00, 5초마다 1장, 가로 1024px → **60장**
이 중 **43장을 눈으로 판독**했다. 512px로는 게임 안 한글이 안 읽혀서 1024px로 다시 뽑았다.
자막은 영어 자동번역본과 **한국어 자동 자막**(427줄, 중복 제거)을 둘 다 받았다. 다만 스트리머 음성 ASR이라 오타가 매우 심하다 → **아래 표의 근거는 전부 화면(프레임)이고, 자막은 보조로만 썼다.**

> 이 문서에서 「영상」은 위 한 편을 가리킨다. 이전 분석(`2026-09-23-video-patch.md`)은 쇼츠 7편이었고 프레임이 성겼다. 이번엔 한 편을 처음부터 끝까지 봤다.

### 1-5. 공간을 어떻게 다루는가 (요청 항목)

프레임 근거로 4가지 질문에 답한다.

**① 실내인가 야외인가, 둘 다면 관계는?**
→ **구분이 없다.** 울타리로 둘러싼 **땅 한 판**이 전부다(0:20). 방·탕·가게는 전부 **지붕 없이 잘라낸 단면**으로 그려진다 — 다다미 방도 바닥과 미닫이문만 보이고 천장이 없다(0:55, 1:05). 「실내」는 **바닥 재질**(나무 데크·다다미·분홍 타일)일 뿐 별개의 건물이 아니다.
남는 잔디는 버리는 땅이 아니라 **경치용 땅**이다(3:20 바위 정원). 그리고 15:00 손익 카드가 이걸 못박는다 — 다다미 방 #2의 인기 31점 중 **경치가 18점(58%)**. 즉 **바깥(잔디·나무·바위)이 안(방)의 값을 절반 넘게 결정한다.** 이게 실내와 야외를 잇는 유일한 고리다.

**② 공간이 넓어지는 계기와, 넓어질 때 화면**
→ **플레이어가 바닥을 깔아서** 넓어진다(0:35~0:45). 「어디서부터 → 어디까지」 **드래그 한 번**, 가격은 드래그하는 동안 **80G처럼 실시간**으로 뜬다. 한 칸씩이 아니라 **한 줄 전체**가 한 번에 깔린다. 땅 자체(울타리 범위)는 처음부터 화면보다 넓고, 화면 가장자리 **노란 화살표**가 밖에 더 있다고 알려 준다(1:20). 「건물 증축 Lv2」 같은 단계는 **없다.**

**③ 하나씩 놓나, 묶음으로 놓나? 성장으로 읽히게 하는 장치는?**
→ **묶음이다.** 세 겹으로 묶인다.
1. **바닥은 드래그 한 번에 한 줄**(0:45).
2. **배치 모드가 안 꺼진다** — 한 번 고르면 탭·탭·탭으로 연달아 놓는다(0:55→1:05→1:20에서 탕 5개가 한 줄로 생김).
3. **결과도 묶어서 터뜨린다** — 2:00에 「상성 UP」 배너가 방 7~8개 위에 **동시에** 뜬다. 하나 놓고 하나 칭찬받는 게 아니라, **한 줄 깔고 우르르 칭찬받는다.**
그래서 3분만 지나도 방 1개 → 14실이 되고(1:35 띠), 화면이 꽉 차는 것 자체가 보상이 된다.

**④ 우리 「폐공장(폐창고)을 고친 카페」 컨셉은 읽히는가?**
→ **영상 쪽이 이겼다. 우리 쪽은 안 읽힌다.**
영상은 **타이틀 그림 한 장(0:00)**에 김 나는 탕·여관 건물·유카타 손님이 다 들어 있고, 첫 게임 화면(0:20)에도 파란 탕이 한가운데 있다. **「온천 여관」이 1초 만에 읽힌다.**
우리는 시작 화면에 `warehouse`(3×2 갈색 상자)가 잔디에 놓여 있을 뿐이고, 「폐창고를 고쳤다」는 사실은 **인트로 자막에만** 있다(`2026-09-22-fun-reset.md` §2 인트로 6컷). 화면에는 **고치기 전도 없고 고친 티도 없다.** 게다가 우리 진짜 주제는 폐창고가 아니라 **제주 경관(바다·오름 전망)** 인데(`core-principles.md` #8), 그건 첫 화면에서 더더욱 안 보인다.
→ 판정: **폐창고는 「이야기」로는 되지만 「무대」로는 실패다.** 무대가 팔아야 하는 건 제주 경관이다. (조치는 §3 P1-3)

### §3-0. 공간 구조를 어느 쪽으로 정할 것인가 — **(B) 야외 중심. 실내는 주방·카운터만.**

#### 먼저, 지금이 왜 어중간한지 (숫자)

코드를 세어 봤다.

| 항목 | 실측값 | 확인 방법 |

**61 대 7이다.** 그런데 `src/sim/rooms.ts`는 **618줄**을 써서 증축 Lv1→4(₩300만/₩800만/₩2,000만), 2층(₩1,500만), 별관, 본관 옮기기(월 1회 ₩200만), 실내 동선 검사(`indoorRouteCheck`)를 굴린다. **7종을 위한 618줄이다.**

그리고 결정적인 것 — `preferIndoor` (`src/sim/rooms.ts:536`):

```ts
export function preferIndoor(state: GameState): boolean {
  if (seasonOf(state.clock.month) === 'winter') return true;   // 12·1·2월 전부
  return activeEvents(state).some((e) => BAD_WEATHER.test(e.id));
}
```

그리고 `filterSeatsForWeather`는 실내 좌석이 **하나라도 있으면 야외를 통째로 버린다.**
→ **1년의 3개월(25%) 동안 야외 좌석 61종이 죽고, 게임이 3칸짜리 방으로 빨려 들어간다.**
(이건 이미 터진 적이 있다 — 개인 메모리 `project_main_expand_moves_door_front`: 「겨울(실내 우선)마다 손님 0」.)

**이게 사용자가 느낀 어중간함의 정체다.** 실내는 **콘텐츠가 없는데 규칙만 세고**, 야외는 **콘텐츠가 다 있는데 겨울마다 꺼진다.**

#### 영상이 주는 답

영상엔 실내/야외 구분이 **아예 없다**(§1-5 ①). 땅 한 판, 바닥 재질만 다르고, 지붕은 안 그린다. 그리고 방의 값 31점 중 **18점(58%)이 바깥 경치**다(15:00).
즉 카이로는 「실내를 늘린다」가 아니라 **「바깥을 가꿔서 안의 값을 올린다」**로 설계했다.

#### 그래서 (B)를 고른다 — 근거 4개

1. **데이터가 이미 (B)다.** 61:7. (A)로 가려면 실내 시설 40종 이상을 새로 만들어야 한다. 「추가하지 말고 덜어내라」에 정면으로 어긋난다.
2. **우리 차별화 축이 야외에만 있다.** `core-principles.md` #8이 못박은 축은 **「제주 관광 생태계 + 경관(바다·오름 전망)」**. 실내 테이블은 바다를 못 본다. `site.ts`의 `view`(전망 반경 3)·`shade`(그늘)·`SEA_SCENERY`(6)·`OREUM_SCENERY`(4)는 전부 야외 좌석 전용(`isOutdoorSeat`, `src/sim/site.ts:231`)이다. **실내를 키우는 건 우리 유일한 차별화 축을 끄는 짓이다.**
3. **(C)는 이미 해 봤고 그게 지금이다.** 「둘 다 두되 역할을 나눈다」가 현재 코드의 의도였다(겨울=실내, 여름=야외). 결과는 3칸짜리 실내와 죽은 겨울. **(C)를 다시 고르는 건 같은 실수의 반복이다.**
4. **영상이 (B)에 가깝다.** 카이로도 「건물 안」이 아니라 「깔린 바닥 위」에 다 놓는다.

#### (B)의 정의 — 한 문장

> **손님이 앉는 곳은 전부 마당이다. 본관은 주방과 카운터만 있는 3×2 상자로 고정한다. 추위·비는 「실내냐 야외냐」가 아니라 시설이 가진 「지붕·바람막이」 속성으로 막는다.**

### P0 — 이번 판에 반드시

#### P0-1. 바닥(올렛길·데크)을 **드래그로 한 줄** 깐다 + 가격을 드래그 중에 보여 준다

- **왜** — 영상 0:35~0:45. 「어디서부터 → 어디까지」 두 번 탭에 복도 한 줄이 깔리고, 끄는 동안 **80G**가 실시간으로 뜬다. 사용자가 말한 **「야외에만 하나씩 늘리지 말든가」의 직접 답이다.** 지금 우리는 올렛길을 한 칸 ₩1만씩 탭해야 한다.
- **무엇을**
  - 짓기에서 `path`(올렛길)·`stonewall`(돌담)·`railing`(난간) 같은 **1×1 선형 물건**은 **드래그 배치**로 바꾼다. 시작 칸 누르고 → 끌고 → 떼면 그 직선(ㄱ자 포함)이 한 번에 깔린다.
  - 끄는 동안 하단 한 줄에 **「어디까지 놓을까요? · ₩N만」** — N은 `칸 수 × def.cost`로 매 프레임 갱신. 돈이 모자라면 그 줄이 빨개지고 놓이지 않는다.
  - 놓을 수 없는 칸은 그 칸만 건너뛴다(전체 취소 아님).
- **어디를**
  - 새 함수 `dragFootprint(state, type, from, to): Pt[]` — `src/sim/grid.ts`. `footprint`/`canPlace` 옆에 둔다.
  - 새 액션 `{ type: 'placeLine', objectType, from, to }` — `src/sim/types.ts` 액션 유니온 + `src/sim/apply.ts`. 내부는 칸마다 기존 `canPlace` → `placeObject` 반복(규칙 재발명 금지).
  - 가격 미리보기 — `src/ui/PlacementHints.tsx`에 `linePreview` 추가, 문구는 `src/ui/MessageLine.tsx` 한 줄.
  - 대상 판정 — `src/data/index.ts`에 `LINE_PLACE_KINDS = new Set(['path', 'path_wall', 'wall'])`.

#### P0-2. **배치 모드를 연속으로** — 한 번 고르면 짓기 창으로 안 돌아간다

- **왜** — 영상 0:55 → 1:05 → 1:20. 탭·탭·탭으로 탕 5개가 한 줄로 생긴다. 창을 다시 여는 동작이 0번이다. 이게 「묶음으로 놓는다」의 절반이다.
- **무엇을**
  - 시설을 놓아도 **고스트가 남고 배치 모드가 유지된다.** 나가려면 「뒤로」를 누르거나 다른 곳을 두 번 탭.
  - 하단 바는 영상과 같은 3정보로 고정: **「〈물건 이름〉 · 위치(x,y) · ₩N만」**. 지금 짓기 창을 다시 열어야 보이는 값이다.
  - 돈이 떨어지면 하단 줄이 **「돈이 모자라요 — ₩N만 필요」**로 바뀌고 고스트가 빨개진다(모달 금지 — 영상 2:15이 하단 한 줄로만 알린다).
- **어디를** — `src/ui/Shell.tsx`(짓기 창 닫는 지점)와 배치 상태를 들고 있는 `src/ui/store.ts`. 시뮬은 안 건드린다.

#### P0-3. 겨울 실내 강제를 지우고 **「지붕(shelter)」 속성**으로 바꾼다

- **왜** — §3-0에서 잰 대로 `preferIndoor`가 **1년 중 3개월 동안 야외 좌석 61종을 끈다.** 실내 좌석은 3종·3칸뿐이라 게임이 그 3칸으로 빨려 들어간다. 영상엔 이런 스위치가 없다 — 겨울(23:40)에도 손님은 **노천탕에 그대로 들어간다.** 온천은 오히려 겨울이 성수기다.
- **무엇을**
  - `ObjectDef`에 `shelter?: 0 | 1 | 2` 추가 — 0 없음 / 1 반쯤(파라솔·차양) / 2 완전(온실·천막·본관).
  - 좌석의 겨울·비 만족 보정을 **이 숫자로만** 계산한다:
    `추위감점 = (겨울 또는 악천후) ? (2 - shelter) × SHELTER_PENALTY : 0` (`SHELTER_PENALTY = 6` 제안 — 지금 `SAT_SHADE_WINTER = -4`와 같은 눈금)
  - **좌석을 걸러내지 않는다.** 손님은 겨울에도 야외에 앉되 **지붕 없는 자리는 만족이 깎인다.** → 플레이어의 대응은 「실내로 도망」이 아니라 **「파라솔·온실·화로를 깐다」**가 된다. 이미 있는 `fire_pit`(화로석, 4인)이 겨울 주인공이 된다.
  - 기존 `table_parasol`은 `shelter: 1`, `fire_pit`은 `shelter: 1` + 겨울 보너스, 새 온실 좌석은 `shelter: 2`.
- **어디를**
  - `src/sim/rooms.ts` — `preferIndoor`·`filterSeatsForWeather` **삭제**, `guests.ts:30`의 import도 정리.
  - `src/sim/site.ts` — `siteBonus`에 `shelter` 항 추가(`SAT_SHADE_WINTER` 바로 옆).
  - `src/data/objects.json`·`generated/objects.json` — 좌석·차양류에 `shelter` 값.
  - **검증**: 헤드리스로 옛 규칙 vs 새 규칙을 돌려 **12·1·2월 손님 수가 0이 아니고** 여름 대비 60% 이상인지 본다(메모리 교훈: 「guests 0인 달은 canOpen·freeSeats부터 의심」).

#### P0-4. **시설 손익 카드**에 「합계」 줄 · 「누구에게 인기」 · 페이저를 붙인다

- **왜** — 영상 15:00이 이 영상 전체에서 가장 밀도 높은 화면이다. 방 하나에 〈유지/월 10G · 기본 15/40G · 보너스 16/3G · **경치 18** · 합계 31/43G · 「고령자에게 인기」〉가 다 있고 **1/4 페이저로 다음 시설로 넘어간다.** 「이 자리가 지금 얼마나 일하고 있나」를 창 하나에서 다 판단한다. 우리 `ObjectInfoPanel`은 조각은 다 있는데 **합계가 없어서 합산이 안 되고**, 시설끼리 비교하려면 맵을 돌아다니며 하나씩 탭해야 한다.
- **무엇을**
  1. **「합계」 줄 추가** — 기본 + 코너 보너스 + 경치 + 아이템 보너스를 더한 **인기 합계 / 요금 합계**를 굵게. 지금 화면의 숫자들과 같은 줄에 놓아 **덧셈이 눈에 보이게** 한다.
  2. **「누구에게 인기」 한 줄** — `guestTypeDef`의 태그와 대조해 가장 잘 맞는 손님층 1개를 「젊은 손님에게 인기」처럼. (영상: 「고령자에게 인기」)
  3. **페이저 `n/N`** — 카드 좌우 화살표로 **같은 종류의 다음 시설**로 이동 + 맵 카메라가 따라감. 영상 15:00의 `1/4`.
  4. **경치 줄을 제일 굵게** — 영상에서 경치가 31점 중 18점이다. 우리도 `sceneryScore` 기여를 다른 줄보다 큰 글자로.
- **어디를** — `src/ui/ObjectInfoPanel.tsx` (`Stat` 줄들이 있는 72~84행 근처). 숫자는 `objectStats`·`sceneryScore`가 이미 준다 — **새 계산 없음, 합치고 정렬만 한다.**

#### P0-5. 손님 하나가 끝날 때 **영수증 한 줄**

- **왜** — 영상 3:00 / 18:40 / 29:40. 손님이 나갈 때마다 하단에 〈얼굴 · 대학생 · 인기 +6 · 소지금 +9G〉가 뜬다. **30분 내내 끊기지 않는 초 단위 보상**이고, 「누가 얼마를 내는가」가 손님층 선택(7:40)과 바로 이어진다. `core-principles.md` 원칙 2가 요구하는 「초 단위 층」이 우리는 비어 있다 — `VoiceFeed`는 말만 하고 숫자가 없다.
- **무엇을** — 손님 퇴장 시 한 줄: **`[얼굴] 〈손님층〉 · 인기 +N · ₩N`**. 2초 뒤 사라지고 다음 줄로 교체. 러시 중엔 뜨지 않는다(HUD가 이미 꽉 참).
- **어디를** — `src/ui/VoiceFeed.tsx`에 숫자 슬롯 추가(새 컴포넌트 만들지 말 것). 값은 `src/sim/guests.ts` 퇴장 처리에서 `{ typeId, repGain, paid }`를 이벤트로 흘려 준다.

## §5. 못 본 것 · 추정 표시

정직하게 적는다.
